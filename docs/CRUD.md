## 0. 이 문서의 목적

`CLAUDE.md` § 3 Stage 3 — "`docs/CRUD.md`는 화면×테이블 CRUD 매트릭스로 유지한다. **(배선 누락 검출용)**"

따라서 이 문서는 예쁜 표가 목적이 아니다. **저장되는데 아무 화면도 읽지 않는 컬럼**과
**화면이 필요한데 저장할 곳이 없는 값**을 찾아내는 것이 목적이다. § 4 · § 5 가 그 결과다.

### 화면 목록의 출처

`main` 에서 "화면 목록 + URL 매핑" 계약은 **보류 상태**다 (`CLAUDE.md` § 4.2 계약 1번 — UI 세션과
JSP 배선 세션이 각자 기록한 뒤 PM이 대조해 확정). 아직 양쪽 모두 미기록이다.

아래 화면 목록은 그 계약이 아니다. **입력 사양 두 건에서 역산한 목록**이며 `main` 의 계약을 선점하지 않는다. URL 은 매트릭스의 행을 식별하기 위한 표기일 뿐이고,
실제 Servlet 매핑은 JSP 배선 트랙이 정한다.

## 5. 데이터 흐름 추적 — 입력 → 저장 → 재사용

ERD 트랙의 본래 과제다 (`CLAUDE.md` § 2 항목 7 — "입력받은 각 데이터의 **저장과 사용**").
화면에서 들어온 값이 어디에 앉고 어느 화면에서 다시 나오는지를 끝까지 따라간다.

| 입력 화면 | 입력 값 | 저장 위치 | 다시 쓰이는 화면 |
|---|---|---|---|
| 회원가입 | 아이디 · 비번 · 이름 · 이메일 · 연락처 | `member.*` | 로그인, 헤더, 마이페이지, **주문서 기본값**, 관리자 회원관리 |
| 배송지관리 | 별칭 · 받는사람 · 연락처 · 우편번호 · 주소 | `address.*` | **주문서 자동입력** (`is_default='Y'`) |

| `data.sql` | 배송비 · 무료배송기준 · 점검모드 · 재고부족기준 | `system_config` | 장바구니·주문서 금액 계산, 헤더 점검 판정, 대시보드 |

## 6. 추적이 끊긴 지점 — 3건 해소

§ 5 를 따라가다 **저장은 되는데 어느 화면도 읽지 않는** 값 3개가 나왔다.
세 건 모두 **테이블 변경 없이 화면·권한 쪽에서 해소**됐다. 아래가 적용된 결론이다.

### 6-1. `delivery_history.is_forced` → `/dev` 가 읽는 시연용 값

**결론: `/dev` 라우팅 페이지에서 컨트롤하는 시연용 값이다. 고객 화면에는 노출하지 않는다.**

읽는 화면을 **30번 `/dev` 상태 컨트롤러**로 확정했다. 강제 변경을 거는 곳과 그 결과를 확인하는 곳이
같은 화면이므로, 상태를 비틀고 이력에 `'Y'` 로 찍히는 것을 그 자리에서 바로 본다.

처음 권장했던 "11번 주문상세 타임라인에 표시"는 **버렸다.** 실제 쇼핑몰에서 고객에게
"이 배송완료는 운영자가 강제로 만든 것"이라고 알리는 것은 의미가 없고, 오히려 내부 조작 흔적을
외부에 흘리는 설계가 된다. `is_forced` 는 시연 보조 장치이지 고객 정보가 아니다.

| | |
|---|---|
| 쓰는 곳 | 8번 결제처리(`'N'`) · 25번 관리자 주문관리(`'N'`) · 30번 `/dev` 상태 컨트롤러(`'Y'`) |
| 읽는 곳 | **30번 `/dev` 상태 컨트롤러** |
| 노출 안 함 | 11번 주문상세 배송 타임라인 (고객) |

### 6-2. `admin_log` → 감사로그 조회 화면 추가

**결론: 전용 조회 화면을 만든다.** → **36번 `/dev/log`** (§ 3 매트릭스에 추가)

`admin_log` 를 쓰는 화면이 10개인데 읽는 곳이 범용 테이블 덤프(31번)뿐이라
`action` 별 필터·기간 조회가 불가능했다. 조회 화면을 두면 `detail` 컬럼(변경 전 → 후)이 처음으로 쓰인다.

조회 화면이 갖출 것:

| 항목 | 내용 |
|---|---|
| 필터 | `mode`(ADMIN / DEV) · `action`(§ `ERD.md` 2.17 의 16종) · 기간(`created_at`) · `target_table` |
| 정렬 | `created_at DESC` 고정 — 감사 로그는 최신순 외에 볼 이유가 없다 |
| 조인 | `member` 를 조인해 `login_id` 를 함께 보여준다. `member_id` 숫자만으로는 못 읽는다 |
| 페이징 | `paging*` 컴포넌트 재사용 (`css/DECISIONS.md` D-09) |

**덤으로 닫히는 구멍이 하나 있다.** `ERD.md` § 8 쟁점 7 — `/dev` 가 `login-as` 로 남의 세션을 쓰면
`admin_log.member_id` 에 전환된 회원이 찍혀 실제 행위자가 사라지는 문제다. 조회 화면에서
`detail` 의 `impersonated_by` 를 같이 보여주면 추적이 복원된다. 조회 화면이 없으면 그 값도 묻힌다.

> 22번 대시보드에 "최근 조작 N건"을 띄우는 값싼 대안도 있었으나, 필터가 없으면
> `detail` 을 활용할 수 없어 채택하지 않았다. 둘은 양립하므로 대시보드 위젯은 나중에 더해도 된다.

### 6-3. `review.item_id` → 작성 선택 · 권한 비대칭으로 해소

**결론: 리뷰 작성은 강제되지 않는다.** 구매자는 자신이 구매한 상품에 대해 **구매 건당 1회** 쓸 수 있고,
**쓰지 않아도 된다.** 조회는 전체 공개이고, **ADMIN 은 삭제만 되고 수정은 안 된다.**

#### 권한 매트릭스

| 동작 | 작성자 본인 | 다른 사용자 | ADMIN |
|---|---|---|---|
| 작성 **C** | ○ 구매 건당 1회 · **선택** | ✕ | ✕ |
| 조회 **R** | ○ | **○ 공개** | ○ |
| 수정 **U** | ○ | ✕ | **✕** |
| 삭제 **D** | ○ | ✕ | **○** |

ADMIN 에게 U 를 주지 않는 것이 이 규칙의 핵심이다. 남의 글 내용을 고치는 경로를 아예 만들지 않고,
부적절한 리뷰는 **내리는 것**으로만 처리한다. 그래서 35번 관리자 리뷰관리 화면은 `rvw` 에 **R · D 만**
갖는다 (§ 3 매트릭스).

#### `item_id` 가 드러나는 지점

제약으로만 있던 `item_id` 가 아래 세 곳에서 실제로 쓰인다.

| 화면 | 쓰임 |
|---|---|
| 11번 주문상세 · 17번 내 리뷰 | `item_id` 로 리뷰 존재를 조회해 **"리뷰 쓰기" / "작성 완료"** 를 분기 (`OrderItemDTO.reviewWritten`) |
| 5번 상품상세 리뷰목록 | **"구매자 작성"** 배지. `item_id` 가 NOT NULL 이므로 모든 리뷰가 구매 확인된 것이다 |
| 35번 관리자 리뷰관리 | 리뷰에서 역방향으로 주문 건을 찾아가는 경로 |

#### ERD 는 바꾸지 않는다

"선택 작성" 을 담으려고 컬럼을 더할 필요가 없다. **리뷰 행의 부재가 곧 "안 씀"** 이고,
`item_id` 의 UNIQUE 가 "1회" 를 보장한다. § 1 ERD 의 `ORDER_ITEM ||--o| REVIEW` 가 이미
0..1 (선택적 1개) 로 그려져 있어 애초에 맞게 설계돼 있었다. 빠져 있던 것은 **화면과 권한 규칙**뿐이다.

## 7. 화면에 필요한데 저장할 곳이 없는 값 — 1건

### `product` 평균 별점 · 리뷰 건수

4번 상품목록과 5번 상품상세가 평균 별점을 보여줘야 하는데(`ERD.md` § 7 `ProductDTO` 의
`avgRating` · `reviewCount`) 저장 컬럼이 없다.

**판단**: 컬럼을 **추가하지 않는다.** `review` 에서 집계한다.

```sql
SELECT AVG(rating), COUNT(*) FROM review WHERE product_id = ?
```

목록 화면은 상품마다 이걸 돌리면 N+1 이 되므로, 목록 쿼리에 `LEFT JOIN` + `GROUP BY` 로 한 번에 받는다.
비정규화 컬럼(`product.avg_rating`)을 두면 리뷰 C/U/D 마다 갱신해야 하고, 그 갱신을 빠뜨린
화면이 하나라도 생기면 틀린 별점이 영구히 남는다. 샘플 규모에서는 집계가 싸다.
